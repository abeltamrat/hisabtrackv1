# HisabTrack project audit — 5 October 2026

HisabTrack has substantial functionality, but the current working tree is not ready to be trusted as an authoritative financial record. The largest risks are cross-user data retention, permissive shared-data rules, unreliable synchronization, and accounting operations that can partially succeed. Successful compilation does not resolve these problems.

This review covers architecture, cash flow, balances, loans, budgets, recurrence, forecasts, SMS imports, loading behavior, storage scope, security, privacy, backups, and release configuration. It reviews the existing working tree, including its many pre-existing uncommitted changes. Application source was not changed during this audit.

**Verification and limits**

- `npx tsc --noEmit --pretty false`: passed.
- `node --check functions/index.js`: passed.
- Production web export: passed, with 39 static routes and a 4.82 MB main JavaScript bundle before transport compression. Output was written outside the repository to `%TEMP%/hisabtrack-analysis-web`.
- Focused Node checks transpiled and executed the actual forecast, transfer-pairing, budget, and backup-validation functions. Results are recorded below. The zero-interest check evaluated the exact formula from the calculator.
- The web export warned that the Google Sign-In package method used is not implemented in its ordinary web distribution. Web sign-in needs interactive verification.
- No Android device/emulator run, interactive browser walkthrough, Firestore emulator test, deployed-rule inspection, production-data access, or dependency vulnerability audit was performed. Security-rule findings describe the checked-in rules if deployed. Concurrency findings are code-supported failure scenarios, not device-level reproductions.
- The repository contains a template component snapshot test, but no configured test script or meaningful financial regression suite was found. The top-level `__tests__` directory contained no discovered test files.

**Architecture and current data flow**

This is an Expo 54 / React Native 0.81 / React 19 TypeScript application, not a PHP/MySQL application. XAMPP is simply its current filesystem location. Expo Router supplies the screens. Redux stores accounts, transactions, budgets, and loans; React contexts hold authentication, categories, settings, theme, and app lock.

Native financial records live in `hisabtrack.db`; web financial records live in IndexedDB. SQLite stores most entities as JSON blobs, with indexed transaction columns for account/date filtering. AsyncStorage, web localStorage, SecureStore, and static service fields hold other data. Firebase provides authentication, cloud copies of four financial collections plus categories, shared loans/chat/repayments, and notification infrastructure. Cloud Functions send queued push notifications and scheduled loan reminders.

The normal transaction flow is screen → Redux thunk → database transaction/balance update → local-change event → UI refresh and whole-collection cloud sync. SMS follows permission → sender scan → parser/optional AI → persisted draft → user acceptance → transaction, sometimes also a loan. This separation is useful, but operations spanning multiple stores have no common commit boundary.

Positive foundations include a typed database interface, native transaction indexes, atomic transaction-and-balance writes on web, explicit SQL transactions on native, serialized SMS/draft work in several paths, human review of SMS drafts, and UID-based ownership for the main Firestore user subtree. These should be retained while correcting the problems below.

**Priority findings: user isolation, security, and privacy**

1. **High — logout leaves financial data accessible to a subsequent user.** `contexts/AuthContext.tsx:112` clears the database and calls `StorageService.clearAll()`, but `utils/storage.ts:29` removes only categories, native recurring rules, and an obsolete notification key. It does not clear `draft_transactions`, `app_notifications`, SMS learning/calibration data, or web `recurring_transactions` and `app_settings`. Drafts include full SMS text. `services/AIFinancialAssistant.ts:103` also retains static chat history; logout does not call its reset method. Account IDs are not a substitute for a user namespace. Partition every store and in-memory cache by UID, cancel user-specific background work, and perform a complete session teardown before showing another user's screens. Cancel scheduled local notifications as part of that teardown.

2. **High — the phone directory can be overwritten by another authenticated user.** `firestore.rules:12` verifies only that the incoming document UID equals the caller. It does not verify ownership of an existing entry or possession of the phone number. A user can claim another person's phone document by writing their own UID. Authenticated users can also enumerate the directory because `read` allows both document reads and queries. The index stores email and UID. Use verified phone ownership and a trusted, rate-limited lookup/write boundary. The existing rules also prevent unauthenticated phone lookup, while `app/(auth)/login.tsx:85` relies on that lookup before sign-in; phone-based login therefore conflicts with these rules.

3. **High — shared-loan rules do not enforce the intended consent and repayment model.** In `firestore.rules:33`, a creator is not required to start a loan in `PENDING`. The initiator update branch can set `linkStatus` to `ACCEPTED` without counterparty consent. Repayment creation can supply `CONFIRMED` immediately; repayment updates require a different participant and an allowed status but do not preserve amount, author, or date, nor require a transition from pending. Chat updates permit either participant to rewrite text and sender. These bypass protections in `services/LinkedLoanService.ts`. Require explicit field allowlists, valid amounts/types, immutable identity fields, accepted-link checks, and state-transition rules. Permit chat recipients to change only their own read receipt. Test these rules with two users in an emulator.

4. **High — privacy statements contradict implementation.** `app/privacy.tsx` says full SMS content is neither stored nor transmitted and calls the local SQLite database encrypted. `services/SMSSyncService.ts:403` stores `raw_sms`; `services/SMSAICalibrationService.ts` retains examples; `services/AIFinancialAssistant.ts:1243` sends raw SMS plus up to five calibration examples to configured AI providers. The SQLite setup has no application-level encryption/key configuration. Device encryption may exist, but that is a different claim. The policy describes cloud sync as separately optional, while `AuthContext.tsx:48` automatically pulls and pushes upon sign-in. Update the disclosures to match actual behavior and implement explicit controls for cloud sync and provider-specific data sharing. This is a product/code consistency finding, not a legal compliance opinion.

5. **High — a JSON backup exports configured AI credentials.** `services/BackupService.ts:87` loads the entire settings object and includes it in plain JSON. `contexts/AppSettingsContext.tsx:49` includes Gemini, Groq, and OpenRouter API keys in that object. Native SecureStore protection is lost when those values are exported. Redact credentials by default and restore preferences separately from secrets. Document that exported financial data is unencrypted.

6. **High — reset does not mean complete data erasure.** `SyncService.deleteRemoteData()` removes only accounts, transactions, budgets, loans, and the categories document. It leaves profile/phone-index records, devices, push jobs/receipts, shared loans, repayments, and chat. It does not delete the Firebase Auth identity. `AccountResetService.ts` misses keys such as SMS learning/calibration and the PIN key. It also deletes remote data before stopping auto-sync, permitting active sync work to race with deletion. Define separate operations for financial reset, local device cleanup, and account deletion; specify shared-record retention and implement a server-controlled deletion workflow.

7. **High — session transitions can race with synchronization.** `AuthContext.tsx:101` ends loading before its asynchronous initial sync or null-user cleanup completes. A null auth event launches destructive cleanup without awaiting it. There is no session generation guard around in-flight pulls/pushes. `SyncService.stopAutoSync()` unsubscribes listeners but does not cancel scheduled timeouts or active operations. Delayed work can mutate the global database after logout or account switch. Introduce a UID-bound session generation, await initialization/cleanup, and reject results from obsolete sessions. Unexpected auth loss should not silently destroy unsynced local work.

8. **Medium — app lock is a UI layer with a fail-open initialization path.** `AppLockContext.tsx` starts unlocked, renders children while preferences load, and on preference-load failure merely marks them loaded. `AppLockService.ts` calls SecureStore directly without web handling. The four-digit PIN has no attempt limit and uses a fixed-prefix SHA-256 hash. Render a neutral gate until lock state is established, handle unsupported platforms explicitly, and add bounded attempts/backoff. This lock does not encrypt the database. Review screenshot/app-switcher exposure separately on devices.

9. **High before distribution — release/update configuration needs correction.** `android/app/build.gradle` signs the local release variant with the debug keystore. Both `app.json` and `UpdateService.ts:5` configure the binary update manifest over HTTP, and the manifest controls the download URL without an application-level signature check. Android package-signature checks still matter; this is not proof of arbitrary silent installation. Use a proper release key and authenticated HTTPS update metadata. The native Android manifest also contains a different Expo update project URL from `app.json`, so native and generated build configurations disagree. Inspect the final merged manifest and actual release artifact, including requested permissions and backup policy, before distribution.

10. **Medium — unnecessary global push rule.** `firestore.rules:81` allows every authenticated user to read/write every `pushDevices` document. Current client and server code instead use `users/{uid}/devices`. Remove the unused global rule or enforce document ownership. The actual token collection is protected by the user-subtree rule; exposure of live tokens in the global collection was not verified.

**Cash flow, balances, and financial mathematics**

The database convention is: income adds `amount`; expense subtracts `amount`; transfer debits `amount` from the source and credits `amount - fees - tax` to the destination. That convention can work if every producer stores the gross source debit consistently. The transfer itself should be cash-neutral apart from its fees. Reports must represent those fees somewhere.

| Event | Cash effect | Income/expense interpretation needed |
|---|---|---|
| Opening balance | Establishes starting cash | Exclude from earned income and current-period savings |
| Salary | Increases cash | Operating income |
| Purchase | Decreases cash | Operating expense |
| Own-account transfer | Moves cash; fees reduce total cash | Principal excluded; fees included as expense |
| Borrowed principal | Increases cash and liability | Financing inflow, not earned income |
| Lending principal | Decreases cash and increases receivable | Lending outflow, not consumption expense |
| Principal repayment | Changes cash and debt/receivable | Financing movement; separate interest |
| Balance correction | Reconciles records | Explicit adjustment, not ordinary earnings/spending |

11. **High — cash movement and economic income are conflated.** `store/slices/accountsSlice.ts:29` creates opening balances as ordinary INCOME/EXPENSE; edits create balance adjustments the same way. `app/loans.tsx:560` represents borrowed principal as INCOME and lent principal as EXPENSE. Dashboard and report savings calculations sum those types indiscriminately. Adding an existing 10,000 balance can show 10,000 income and 100% savings without earning anything. Borrowing can improve the apparent savings rate. Add a stable transaction purpose/cash-flow classification rather than relying on editable category names. Present operating, financing, and adjustment totals separately.

12. **High — transfer fees reduce cash but disappear from reported expenses.** `services/database/web.ts:117` and native `balanceDelta()` subtract transfer fees from the destination credit. `app/(tabs)/index.tsx:108` and `reports.tsx:274` count only INCOME and EXPENSE. A 1,006 gross transfer with 6 fees changes combined cash by -6, but reports show zero expense/net movement. This also invalidates dashboard `prevBalance = balance - thisMonthNet`. Record fees as an explicit expense posting or include them consistently in all cash-flow/report calculations without double-counting.

13. **High — the loan-detail schedule violates its own arithmetic.** `app/loan/[id].tsx:99` initializes balance to principal plus all interest, then subtracts only each row's principal. The last row sets principal to the remaining total but leaves payment unchanged. For principal 1,200, annual interest 10%, and 12 months, it shows payment 110, interest 10, and a final principal of 220: principal + interest is 230, not 110. Track principal balance from 1,200, or track total debt and subtract the full payment. Round consistently and adjust the final payment so row and total identities hold.

14. **Medium — zero-interest amortization is broken.** `app/amortization.tsx:85` accepts a zero rate but evaluates a formula with a zero denominator. A 1,200 loan over 12 monthly periods returns `NaN` rather than 100. The direct formula check reproduced this. Use `P / n` for zero interest, require a valid whole number of installments or define a partial final period, and reject non-finite inputs/results.

15. **High — loan/cash writes can partially succeed and retries can double-charge.** The ordinary repayment flow updates loan balance first and creates the cash transaction second (`app/loans.tsx:794`). Transaction failure leaves a paid-down loan with unchanged cash. Linked repayment recording/confirmation creates a local transaction before updating Firestore (`app/loan/[id].tsx:234`), with no durable repayment-to-transaction idempotency key. A network failure followed by retry can duplicate the cash entry. Several `await dispatch(addTransaction(...))` calls omit `.unwrap()` or rejected-action checking, so Redux rejection is treated as success. Implement a local atomic loan/payment operation and a durable outbox for remote confirmation, keyed by repayment ID. Preserve the distinction between cash actually moved and a disputed claim.

16. **Medium — loan terms need a declared interest policy and stronger validation.** The loan screens use flat simple interest based on whole calendar months with a minimum one-month charge; the standalone calculator uses reducing-balance periodic amortization or monthly compounding for one-time payment. These are different products, not interchangeable answers. Partial-month periods are truncated, overpayments clamp debt to zero while recording the entire cash amount, and edits to principal/paid amount do not reconcile historical cash transactions. Persist the interest method, day-count basis, rounding policy, and payment allocation. Model excess payment/refund explicitly or reject overpayment.

17. **High — recurring work may be skipped after write failure.** `app/recurring.tsx:406` awaits dispatch without checking rejection and advances `nextDate` and `completedRepetitions` regardless. Its outer `Promise.all` also launches rules concurrently against the native database. A failed posting can therefore be marked completed. Commit the transaction and occurrence cursor together, use a unique `(ruleId, occurrenceDate)` key, and advance only after success.

18. **Medium — end-of-month recurrence drifts.** `ForecastService.ts:290` and `app/recurring.tsx:596` use `setMonth(currentMonth + 1)`. Executing the actual forecast increment gave January 31, 2026 → March 3, 2026. February is skipped and the anchor day changes. Preserve an original recurrence anchor with an explicit end-of-month policy; use the same scheduler for forecasts, catch-up, and notifications. Define leap-day behavior too.

19. **Medium — forecast is an incomplete cash scenario.** `ForecastService.ts:70` starts from all account balances, including locked funds. It models borrowed debt as one full payment on the due date, excludes overdue debt and expected lent-loan collections, and does not link recurring repayments to loan obligations. A scheduled repayment plus its loan due event can count the same payment twice. Explain these assumptions in the UI or implement account-linked obligations and payment schedules. Missing transfer destinations can also make account projections disagree with the unchanged total. Enforce the invariant that projected account balances sum to the projected total, including explicitly labeled virtual obligations.

20. **Medium — currency is primarily presentation, not accounting.** `app/accounts.tsx:602` creates accounts with USD even when global display settings use another currency. Dashboard/forecast aggregate raw amounts without conversion; transactions and loans lack their own currency/FX snapshots. Relabeling amounts is not conversion. Either enforce a single ledger currency throughout, or preserve original amounts/currencies plus booked exchange rates and calculate base-currency totals.

21. **Medium — money and validation are inconsistent at the persistence boundary.** Monetary values are JavaScript numbers/SQLite REAL; some paths round, others do not. Database transaction builders validate a transfer destination but do not comprehensively validate finite positive amounts, nonnegative fees/tax, existing accounts, distinct transfer endpoints, or fee totals. UI checks do not protect imports, sync, or alternate callers. Use integer minor units or a decimal model, centralized domain validation, and currency-specific precision.

22. **Medium — budget indicators have edge cases.** `BudgetService.ts:136` reports zero progress when effective limit is zero, even with positive spending; the actual function returned 0 for spending 10 against limit 0. Remaining is correctly negative, so different UI indicators can disagree. Transfers' fee expense is also omitted from budget spending. Category-name matching and rename cascades are fragile. Use category IDs, show a clear exceeded state for a zero budget, and define whether rollover can cross missing budget periods.

23. **Medium — financial periods and trends are inconsistent.** Dashboard uses calendar month start with no upper date bound; reports use rolling month/week/year windows, also without an upper bound. Future-dated transactions can enter current totals. Dashboard timestamps are captured once per mount, so an open screen can retain last month's boundaries after midnight. Report daily averages use fixed 30/365 denominators despite calendar window lengths, and monthly averages omit months with no transactions. Use shared explicit `[start, end)` ranges, refresh the clock on foreground/date changes, and include zero-activity months in trend series.

**SMS reconciliation and data integrity**

24. **High — unrelated cash flows can become a transfer.** `utils/transferPairing.ts:60` matches opposing pending drafts on different accounts using amount and a 15-minute interval, without requiring matching counterparty/reference evidence. Actual-function execution paired an unrelated 500 expense and 500 income one second apart. Acceptance then closes both drafts as one transfer (`app/draft-transactions.tsx:384`), hiding income/expense. Treat weak matches as suggestions requiring explicit confirmation; use reference, institution, account evidence, and confidence levels.

25. **High — duplicate detection can drop legitimate SMS transactions.** `SMSSyncService.ts:269` scans all stored drafts, then falls back to same amount/type within six hours without checking `account_id`. Independent equal-value transactions across accounts can be suppressed. The fallback also suppresses repeated purchases on one account when reference data is absent. Scope strong identities by institution/account and retain ambiguous events for review. Pairing and duplicate suppression must be separate operations.

26. **Medium — capped SMS scans can permanently miss history.** `SMSSyncService.ts:199` keeps only the newest 200 messages per sender, then records the successful sync time as `Date.now()` at line 440. Older unprocessed messages fall behind the watermark. Messages arriving during a scan can also fall between scan time and the later watermark. Page through history, use a cursor tied to the last actually processed SMS, and keep a safe overlap with stable deduplication.

27. **High — native transaction concurrency and migration recovery are unsafe.** `services/database/android.ts:214` issues `BEGIN IMMEDIATE` on one shared connection without a write queue; concurrent callers can attempt nested transactions. Category rename explicitly runs transaction updates in `Promise.all` (`context/TransactionContext.tsx:145`), and recurring catch-up does concurrent work. Existing rows are read before the update transaction begins, so concurrent edits can compute deltas from stale values. Serialize writes or use an appropriate exclusive transaction boundary, and read old state inside it. The schema migration at native line 55 renames, creates, copies, and drops outside a transaction; failure after creating the new table can leave the retry skipping the old rows because the new schema already exists. Make migration atomic and versioned with recovery tests.

28. **High — sync cannot reliably distinguish deletion from absence.** Push removes remote records absent from a nonempty local collection; pull deletes old local records absent from a nonempty remote collection. There are no durable tombstones/outbox acknowledgements. Deleting the final local transaction skips remote deletion (`SyncService.ts:123`), allowing it to reappear on pull. A stale device can also delete another device's new records when it pushes its incomplete collection. Client timestamps and a 60-second grace period do not solve this. Use record-level operations, durable deletion markers, revisions, and transactional conflict handling.

29. **High — sync can lose newer edits or silently miss events.** Push overwrites every remote record without checking its revision. Local-change callbacks return while pushing/applying remote, and snapshots arriving within five seconds of a push are skipped without a queued replay (`SyncService.ts:239`). A legitimate change in those windows may remain unsynced until another event. Per-record errors are swallowed, yet `syncNow()` returns `cloudSynced: true`. Maintain durable dirty records, retry failed operations, surface partial failure, and use server revisions rather than device clocks as the sole conflict authority.

30. **Medium — account creation/adjustment is not atomic with its opening/correction entry.** Normal account creation correctly creates an opening-balance transaction, so full balance recalculation preserves that normal flow. My initial concern that all opening balances disappear was too broad. However, `accountsSlice.ts:35` does not unwrap/check the opening-entry dispatch and returns the intended balance even if the entry fails. The same pattern exists in adjustment/deletion. A DB account can be 0 while Redux shows the requested balance. Imported/legacy accounts without balancing entries can also lose non-ledger opening amounts on recalculation. Commit account and opening/adjustment entries together and migrate legacy baselines explicitly.

**Loading, display, backup, and feature completeness**

31. **High — account detail overwrites the global transaction collection with a subset.** `app/account/[id].tsx:39` dispatches the shared `fetchTransactions({account_id: id})`; its fulfilled reducer (`store/slices/transactionsSlice.ts:83`) replaces all `state.items`. Dashboard, budgets, exports, and reports consume that same list. A filtered request completing after an unfiltered request can leave totals based on one account. Read detail data separately or use query-keyed caches/selectors; never replace the canonical full ledger with a filtered view.

32. **Medium — zero, empty, error, and still-loading states are not reliably distinguished.** Dashboard derives totals from initial empty arrays and does not select the slices' loading/error fields. Authentication loading ends before data readiness. Fetches lack request/session identity protection, so old responses can overwrite newer ones. Several callers catch exceptions around dispatch even though Redux returns rejected actions. Use explicit initial-loading/refreshing/error/stale/success states, `.unwrap()` where appropriate, request IDs, and one coordinated refresh boundary. Financial totals should not look like confirmed zero while data is still loading.

33. **High — native backup import uses a runtime-throwing API.** `BackupService.ts:184` calls `readAsStringAsync` from the top-level `expo-file-system` import. The installed package's `src/legacyWarnings.ts:34` implements that export by throwing. TypeScript still passes. Use the supported File API or the explicit `/legacy` import and verify a native round trip.

34. **High — backup validation and restore can corrupt the ledger.** `BackupService.validateBackup()` checks only top-level arrays/version/timestamp. Executing it accepted `{accounts:[{}], transactions:[{amount:-999}], ...}` with an arbitrary version. Restore in `app/settings.tsx:244` upserts records incrementally into the live database without an all-or-nothing transaction or full referential validation. A late failure leaves a mixed old/new dataset. Stage and validate a versioned backup, check IDs/references/amounts, preview conflicts, commit atomically, and reconcile once before resuming sync.

35. **Medium — some visible features are prototypes.** `app/goals.tsx:24` stores goals only in component state; they disappear on remount/restart and have no ledger linkage. `app/cards.tsx:18` renders hardcoded John Doe cards and balances. These routes should be labeled demonstrations, completed, or hidden in production. A successful web export is not evidence that these features persist real data.

36. **Medium — scale and operational reliability need work.** Each local change can trigger whole-collection sequential Firestore writes, and each remote collection snapshot can trigger a full pull of all collections. Native balance updates read all accounts; web account filtering scans all transactions for destination transfers. The 4.82 MB main web bundle merits route-level splitting and lazy loading of heavy export/chart/AI features. Cloud Function push processing checks the creation event's original data rather than transactionally claiming the current job, so redelivery can send twice. Reminder computation uses server-local clock methods and hardcoded `$` formatting rather than an explicit user's timezone/currency. Treat these as follow-up reliability tasks after integrity/security fixes.

**Data scope and privacy inventory**

| Data | Current location and sharing | Scope concern |
|---|---|---|
| Accounts, transactions, budgets, loans | SQLite/IndexedDB; automatically synced under `users/{uid}` after sign-in | Cloud UID scope is present; local DB is one shared store relying on cleanup |
| Categories | AsyncStorage plus cloud meta document | Global local key; name-based references and inconsistent change notification |
| Recurring rules | Native AsyncStorage or web localStorage; included in JSON backup | Not part of ordinary cloud sync; web logout misses its key |
| SMS drafts/raw bodies | AsyncStorage `draft_transactions` | Shared key; logout misses it |
| SMS learning/calibration | AsyncStorage; examples may enter AI prompts | Shared keys; reset/logout coverage incomplete |
| AI credentials/settings | SecureStore on native, localStorage on web; settings included in backup | Plaintext backup secrets and web settings survive logout |
| AI conversation | Static service memory; sent as prompt context | Not UID-scoped or cleared on logout |
| Shared loan/chat/repayment data | Top-level Firestore shared collections | Participant rules exist but field/state permissions are too broad; reset retains records |
| Phone/email lookup | Firestore `phoneIndex` | Authenticated enumeration and overwrite of another person's mapping |
| Notifications/device tokens | Local notifications and `users/{uid}/devices`, push jobs/receipts | Local notification cleanup and remote deletion scope incomplete |
| Goals | React component state only | No durable storage, sync, or backup |

Puter is enabled by default for web settings, and the AI fallback permits it unless explicitly disabled. Thus “no manually entered API key” does not imply every assistant interaction is local. SMS fallback itself is gated on configured keys, but web assistant behavior has a separate provider path. Describe the selected provider and outbound data before use. Raw financial names/amounts also appear in several console logs; redact sensitive diagnostics in release builds.

**Repair order and acceptance criteria**

1. Contain cross-user exposure: UID-scope every store/cache, serialize session transitions, clear scheduled notifications and chat state, and restrict Firestore shared-data/phone rules. Verify user A → logout → user B, expired sessions, failed sign-out networking, and pending background work.
2. Establish an authoritative financial model: minor-unit money, posting purpose, principal/interest split, account references, and defined currency/date rules. Commit compound local operations atomically with durable operation IDs.
3. Replace whole-collection reconciliation with an outbox, revisions, and tombstones. Test two devices offline, simultaneous edits, final-record deletion, failed writes, retry, reset during sync, and new login during an old request.
4. Repair calculations and scheduling: loan rows must satisfy `payment = principal + interest`; principal totals must equal original principal; zero-interest payments must equal `P/n`; transfer net change must equal negative fees; opening balances must not increase earnings; recurrence must retain its anchor.
5. Fix SMS classification/imports and backups: ambiguous pairing needs confirmation; equal purchases remain separate; scans process more than 200 messages without gaps; backup import validates before mutation and exports no credentials.
6. Repair UI data contracts: account views cannot mutate global ledger scope; totals distinguish loading, stale, and error; returning from edits shows reconciled balances; rollover across month boundaries refreshes periods. Persist or hide prototype routes.
7. Verify real Android/web behavior and deployment: native backup round trip, app lock, SMS permissions, merged manifest, release signing, OTA project, secure update delivery, Firestore rule tests, and provider-consent/privacy text.

Do not start with cosmetic refactoring. First make it impossible for another user's data, a partial payment, or a stale sync to become an apparently valid financial total.
